Running oil-motion without an API key: what the deterministic half actually does

I installed oil-motion as a Claude Code skill this week. Before running anything, I had a note describing it as "a lightweight interactive animation library," a plain-JS thing, GSAP-adjacent. Reading the actual SKILL.md took that apart in about thirty seconds: it's not a library, it's an agent skill that drives paid AI video generation (ZenMux's minimax-h3) to produce the connecting motion between confirmed keyframes, then runs that footage through a deterministic pipeline before wiring it to scroll, pointer, drag, touch, or device-orientation input.

I don't have a ZenMux key configured yet, so I couldn't run the part that actually costs money. What I could run, and did, is the other half: extraction, chroma-keying, QA analysis, atlas packing, delivery-format selection, and the pilot-approval integrity gate. That half turned out to be more interesting than I expected, mostly because of a mistake I made along the way.

The setup: a synthetic stand-in, not an AI-generated asset

To exercise the pipeline I needed some footage, so I generated one myself: a flat vector mascot (circle, two dots, a triangle for a nose) rotating a full 360° over a green-screen background, built with PIL and ffmpeg. This is not what oil-motion is meant to consume. The whole point of the AI-generation step is producing the kind of motion a program can't fake: limb rotation, material change, one part occluding another. A shape spinning around its own center is exactly the case a naive CSS rotate() already handles. I'm using it here only to exercise the deterministic tooling, and I want that distinction to be explicit rather than something a reader has to infer.

Running the pipeline caught my own mistake

motion_pipeline.py build source.mp4 build/ \
  --key 00FF00 --cell-width 160 --cell-height 160 --columns 8 --normalize

This does four things in one pass: extract frames, key out the green background, run anomaly analysis, and pack an atlas. I didn't pass --fps, so it defaulted to 24, and my source clip was 12fps. The result: 76 extracted frames where only 38 were actually distinct, each duplicate immediately following its original.

The QA step caught every single one:

{
  "frameCount": 76,
  "summary": { "warningCount": 38 },
  "warnings": [
    { "frame": 1, "type": "near-duplicate", "value": 0.0,
      "message": "frame_00002.png is very similar to its previous frame" },
    ...
  ]
}

The contact sheet makes it obvious at a glance: frame 0000 and 0001 are pixel-identical, then 0002/0003, then 0004/0005, all the way down. This is exactly what a fps mismatch looks like, and the tool named it correctly on the first run rather than silently packing 38 wasted frames into the atlas. That's a small thing, but it's the kind of check that's easy to skip writing and expensive to skip having.

The delivery format it picked matches what the docs claim

The README's own decision table says a small, ring-shaped, frequently-random-access animation should become an alpha WebP atlas rather than a chroma-keyed video. I fed the actual parameters of this asset into the budget script rather than taking that on faith:

motion_budget.py --frames 76 --display 160x160 --dpr 2 \
  --driver pointer --parameter-space circular --time-control scrub \
  --background-owner page
{
  "delivery": { "selected": "alpha-atlas", "reasonCodes": ["random-access-fits-atlas-budget"] },
  "runtime": { "renderer": "css-alpha-atlas", "controller": "frame-scrub" },
  "decodedFrameMemoryMiB": 29.7,
  "passes": true
}

alpha-atlas, exactly as documented, with the actual reasoning (fits the decoded-memory budget for random access) rather than a rule I have to trust blindly. Small thing to verify, but it's the difference between a design doc and a design doc that's actually load-bearing.

The pilot-approval gate survives an actual tamper test

The one design idea in here I hadn't seen before: before any full production run, oil-motion locks a "pilot." It hashes the first frame, last frame, source video, and page-mount evidence into an approval file, and every later step has to check against that file before continuing.

I didn't just read that claim, I broke it on purpose. Approved a pilot, confirmed check-pilot passed clean, then rotated the first frame's PNG by three degrees and reran the check:

错误：firstFrame 工件已变化，Pilot 批准失效：...\frame_00001.png

("Error: firstFrame artifact has changed, pilot approval invalidated.") Exit code 1, no ambiguity. A three-degree rotation is a tiny, almost invisible change, well within the range a lazy re-export or a careless re-encode could introduce by accident, and the gate still caught it. That's the actual guarantee working, not just a claim in a README.

What I didn't test, and why it's the part that matters most

I have not run the AI generation step, and that's the part this skill actually exists to solve: keyframe consistency, whether the model holds a character's proportions across a turn, how often a pilot gets rejected in practice. Everything above is the scaffolding around that step, careful and genuinely verified rather than assumed, but still scaffolding. Whether the generated motion is any good is still open on my end.

Also found: a real bug, unrelated to any of this

While getting the skill running at all, oil_motion_config.py status crashed outright:

UnicodeEncodeError: 'charmap' codec can't encode characters in position 15-18

None of the 13 Python scripts in the repo guard stdout/stderr encoding, and most of their output is Chinese. On a default Windows console (cp1252), that's an immediate crash the first time any of them tries to print. I patched all 13 with a UTF-8 reconfigure guard and reran the upstream test suite: 64 passed before my changes, 64 passed after. Small fix, but it means the skill is actually usable on Windows now rather than crashing on the first status check.
